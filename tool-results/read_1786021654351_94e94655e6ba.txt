    11→## Executive Summary
    12→
    13→1. **ReviewReply-Lite is a tightly-scoped, well-documented $29–$59/mo SaaS for single-location businesses** (restaurants, salons, dental, retail, contractors) that auto-drafts replies to Google/Facebook reviews and sends review requests by SMS/email. The vision is sharp and the buyer persona is concrete: a non-technical owner who has "never built a spreadsheet."
    14→
    15→2. **The documentation suite is genuinely excellent for a pre-launch product** — `Product-Roadmap.md`, `Implementation-Plan.md`, `AGENTS.md`, `Decision-Log.md`, `Data-Handling-Policy.md`, `Landing-Page-Prompt-Pack.md`, and `MOCK-TO-REAL.md` form a coherent operating system with explicit acceptance criteria, escalation triggers, and a running change log.
    16→
    17→3. **The current build is a complete mock-mode demo**, not a production app. Every `lib/integrations/*` file has real API call code written but gated behind `USE_MOCKS=true` (default). The mock-mode path works end-to-end: signup → onboarding → mock Google connect → poll-reviews → AI draft (rule-based, not Claude) → post reply (simulated) → quick-add review request → mock SMS/email → mock billing. No real third-party account exists.
    18→
    19→4. **The single biggest strategic risk is silent scope creep: an "Enterprise" tier ($249/mo, multi-location, organization dashboards) has been built into the code but is NOT in any locked doc, has NO Decision-Log entry authorizing it, and directly contradicts the Product-Roadmap's explicit non-goal: "Multi-location / enterprise dashboards (single-location only for launch)."** It also conflicts with the comparison pages' thesis ("we're simpler because we don't do enterprise").
    20→
    21→5. **Three documented Phase features are silently broken or missing in mock mode**: (a) Facebook Connect (`/api/businesses/[id]/connect/facebook` route is referenced by `OnboardingForm.tsx` but doesn't exist); (b) click-tracking (`/r/[token]` route mentioned in code but never built — Phase 3 acceptance criterion); (c) plan-gating middleware (Phase 4 / Day 27 — never built).
    22→
    23→6. **The locked AI model name `claude-sonnet-4-6` is not a real Anthropic model identifier.** The real-mode `callAnthropic()` will fail at runtime with a 400/404 from Anthropic. This bug is replicated in three locked docs.
    24→
    25→7. **The README.md is essentially empty** (a single line `GOOGLE-MAP-REVIEW-APP` with a UTF-16 BOM, not "ReviewReply-Lite"). Anyone landing on the repo — including the founder, future hires, or beta testers — has no entry point. This is the most visible doc failure.
    26→
    27→8. **Compliance posture is honest but not implemented.** `Data-Handling-Policy.md` explicitly disclaims GDPR/CCPA/SOC2 status (correctly, for a pre-launch product) but its own rules — 30-day deletion on cancellation, OAuth-token encryption, no-PII-in-logs — have **no code enforcing them**. No background deletion job exists. OAuth "encrypted" columns store plaintext mock strings. No audit trail of access.
    28→
    29→9. **Zero automated tests exist** despite `vitest` being configured and AGENTS.md §4 mandating "every `lib/integrations/*` function has at least one test using mocked responses." The `pnpm test` script runs but exercises nothing.
    30→
    31→10. **Differentiation thesis (vs Birdeye, vs Podium) is consistent and defensible** in the docs and comparison pages: simpler, cheaper, no contract, single-location, reviews-only. But the unapproved Enterprise tier dilutes it. Beta testers who see the Enterprise card on the marketing site will reasonably wonder whether the "we don't do enterprise" pitch is real.

    35→## Stated Vision & Target Customer
    36→
    37→### Vision (from `Product-Roadmap.md` §0)
    38→> *"A $29–$59/mo tool that watches a single-location business's Google/Facebook reviews, drafts on-brand AI replies for one-click posting, and automatically requests reviews from recent customers."*
    39→
    40→### Target customer
    41→- **Owner or manager of one location** — restaurant, salon, dental/med spa, retail shop, contractor.
    42→- **Not technical.** Expects something as simple as a text-message app.
    43→- **Has never built a spreadsheet** (this is explicitly called out as a UX constraint — it shaped the entire Phase 3 entry-method prioritization).
    44→- **Time-starved front-counter operator** (will use the app on a phone or tablet between customers).
    45→
    46→### Core jobs the product must do (priority order)
    47→1. Notify the owner the moment a new review arrives.
    48→2. Draft a reply that sounds like a human who runs this business, not a corporate bot.
    49→3. Let the owner post that reply in one tap.
    50→4. Automatically ask recent customers to leave a review.
    51→
    52→### Explicit non-goals for v1 (locked)
    53→- Multi-location / enterprise dashboards (single-location only).
    54→- Review monitoring beyond Google + Facebook (Yelp/TripAdvisor deferred).
    55→- Social media scheduling, SEO tools, anything outside review reply/request.
    56→- Native mobile app (responsive web only).
    57→
    58→### Locked pricing (final, "do not revisit mid-build")
    59→- Starter: $29/mo — 1 location, Google-only, email review requests, 100 requests/mo.
    60→- Pro: $59/mo — 1 location, Google + Facebook, SMS + email review requests, 300 requests/mo.
    61→- Overage: $0.05 per review-request beyond the plan's allotment (Stripe metered).
    62→- Trial: 14 days, card required at signup.
    63→- Beta cohort: exactly 8 businesses, with 5-of-8 activation gate.

   154→### Notable absences
   155→- ❌ `@sentry/nextjs` — Decision-Log notes Sentry was stubbed. Adding it is a Phase 0 / pre-launch task.

   289→## Data Handling Policy — Compliance Posture
   290→
   291→### What the policy honestly covers (`Data-Handling-Policy.md`)
   292→- **Section 1:** Inventory of data held (owner PII, OAuth tokens, end-customer contact, review text, AI drafts).
   293→- **Section 2:** Storage rules — OAuth tokens encrypted at rest; end-customer contact treated as PII, not exported to analytics, not logged in plaintext; database backups follow same encryption.
   294→- **Section 3:** Access rules — only founder + support person have production DB access; secrets in env vars only; 2FA on Stripe/Twilio/Resend dashboards before go-live.
   295→- **Section 4:** Deletion & retention — 30-day end-customer contact deletion on subscription cancellation; immediate OAuth token revocation; full account deletion within 30 days of request.
   296→- **Section 5:** Third-party API compliance — Google Business Profile / Facebook Graph data-use policies; Twilio 10DLC registration accuracy.
   297→- **Section 6:** Honest disclaimer — "This is not a GDPR/CCPA compliance program, a SOC 2 framework, or legal advice."

   299→### Compliance posture assessment
   300→
   301→| Framework | Posture | Notes |
   302→|---|---|---|
   303→| **GDPR** | 🟡 Aspirational | Policy §6 explicitly defers. For EU customers: no DPA template, no subprocessor list, no Article 28 contract template, no EU data-residency option (Supabase default region is US-East). Right-to-erasure / right-to-access have no code path. |
   304→| **CCPA** | 🟡 Aspirational | Same deferral. No "Do Not Sell My Info" link (technically not required since the product doesn't sell data, but California consumers expect a visible opt-out path). No data-deletion request intake process. |
   305→| **HIPAA** | 🟢 Not applicable | Product is not healthcare. If a dental practice enters patient contact info into the review-request tool, that's the practice's responsibility, not ReviewReply-Lite's — but the privacy policy should explicitly disclaim HIPAA-covered use. |
