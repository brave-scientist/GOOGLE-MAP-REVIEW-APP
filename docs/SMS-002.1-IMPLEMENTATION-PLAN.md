# SMS-002.1 Implementation Plan: Production-Grade Customer-Originated SMS Consent & Immutable Consent Evidence

## Executive Summary
ReviewReply has established a robust carrier integration architecture with Telnyx (and isolated Twilio fallback), atomic webhook idempotency, monotonic delivery transitions, and opt-out precedence. However, the initial SMS-002 affirmative consent implementation contained four compliance and design vulnerabilities:
1. Business employees could manufacture customer consent via a single UI confirmation checkbox.
2. The consent ledger was stored in a mutable single row (`CustomerSmsConsent` with `@@unique([businessId, contact])`), overwriting historical evidence upon re-affirmation.
3. `disclosureText` was validated merely by a 10-character minimum length without server-controlled versioning or approved templates.
4. `API_IMPORT` and `MANUAL_ENTRY` could record `EXPRESS_WRITTEN` consent without verifiable provenance metadata.

SMS-002.1 establishes a defensible, customer-originated, immutable SMS consent evidence architecture.

## 1. Current Architecture Findings & Exact Weaknesses

### 1.1 Source Code Audit Findings
| Component | Current Implementation | Flaw / Weakness |
| :--- | :--- | :--- |
| **`prisma/schema.prisma`** | `CustomerSmsConsent` model with `@@unique([businessId, contact])` and fields `(consentType, consentSource, disclosureText, ipAddress, userAgent, consentedAt, revokedAt)` | Overwrites previous consent events upon upsert; no ledger of historical grant/revoke cycles; no approved disclosure template reference. |
| **`src/lib/sms/consent.ts`** | `recordConsent()` upserts the unique row, resetting `consentedAt = new Date()` and overwriting `disclosureText`, `ipAddress`, and `userAgent`. | Loss of immutable evidence; historical provenance destroyed on re-opt-in. |
| **`src/app/api/campaigns/create/route.ts`** | If `consentConfirmed && disclosureText && channel.includes('sms')`, calls `recordConsent()` in a loop for all campaign recipients. | Employee checkbox manufactures legal affirmative customer consent without customer participation. |
| **`src/app/api/review-us-page/send/route.ts`** | If `channel === 'sms' && consentConfirmed && disclosureText`, calls `recordConsent()` in a loop for all recipients. | Same employee manufacturing vulnerability as campaign builder. |
| **`src/components/app/campaign-builder.tsx`** & **`src/app/review-us-page/page.tsx`** | UI checkbox: *"I confirm that all SMS recipients have affirmatively agreed..."* sets `consentConfirmed: true`. | Confuses employee operational statement with consumer affirmative express written consent. |
| **`src/app/api/sms/consent/route.ts`** | Accepts arbitrary `disclosureText` from authenticated business callers as long as `length >= 10`. | Untrusted client can submit arbitrary text as legal disclosure. |
| **`MANUAL_ENTRY` / `API_IMPORT`** | Allows creating `EXPRESS_WRITTEN` consent with arbitrary strings. | Lacks structured provenance (source system, external record ID, original timestamp, import audit trail). |

## 2. Proposed Schema Architecture

### 2.1 Prisma Schema Additions & Modifications

```prisma
// ── Controlled Disclosure Templates ─────────────────────────────
model SmsDisclosureTemplate {
  id          String   @id @default(cuid())
  version     String   @unique // e.g., "v1", "v2"
  purpose     String   @default("REVIEW_REQUEST") // Controlled purpose
  title       String
  bodyTemplate String  // Verbatim standard text with {businessName} token
  isActive    Boolean  @default(true)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  events      CustomerSmsConsentEvent[]
  invitations CustomerSmsConsentInvitation[]
}

// ── Active Consent State Pointer (Fast Lookup) ──────────────────
model CustomerSmsConsent {
  id             String           @id @default(cuid())
  businessId     String
  contact        String           // Normalized E.164 (+1XXXXXXXXXX)
  status         ConsentStatus    @default(ACTIVE)
  consentType    SmsConsentType   @default(EXPRESS_WRITTEN)
  consentSource  SmsConsentSource @default(CUSTOMER_WEB_FORM)
  currentVersion String?          // Latest disclosure version consented to
  lastEventId    String?          // Pointer to the latest immutable event
  createdAt      DateTime         @default(now())
  updatedAt      DateTime         @updatedAt

  business       Business         @relation(fields: [businessId], references: [id], onDelete: Cascade)
  events         CustomerSmsConsentEvent[]

  @@unique([businessId, contact])
  @@index([businessId, status])
  @@index([businessId, contact])
}

enum ConsentStatus {
  ACTIVE
  REVOKED
  UNVERIFIED_LEGACY
}

enum SmsConsentType {
  EXPRESS_WRITTEN
  TRANSACTIONAL
  IMPLIED
}

enum SmsConsentSource {
  CUSTOMER_WEB_FORM      // Customer consented via ReviewReply secure consent page
  VERIFIED_API_IMPORT    // External system import with verified evidence provenance
  IN_PERSON_KIOSK        // Customer signed on dedicated kiosk
  CHECKOUT_FORM          // Customer checked box during customer checkout flow
  LEGACY_IMPORT          // Unverified legacy records (cannot authorize commercial SMS)
  STAFF_RECORDED         // Staff operational note (not valid for commercial SMS)
}

// ── Immutable Consent Event Ledger (Audit Proof) ────────────────
model CustomerSmsConsentEvent {
  id                  String           @id @default(cuid())
  consentId           String?
  businessId          String
  contact             String           // Normalized E.164
  eventType           ConsentEventType // GRANTED, REVOKED, REGRANTED, IMPORTED, MIGRATED_LEGACY
  consentType         SmsConsentType
  consentSource       SmsConsentSource
  disclosureTemplateId String?
  disclosureVersion   String           // e.g. "v1"
  disclosureText      String           // Verbatim exact text presented at that moment
  ipAddress           String?
  userAgent           String?
  sourceUrl           String?          // e.g. "/consent/abc123"
  externalSystem      String?          // For API imports (e.g. "Shopify POS", "Square")
  externalRecordId    String?          // ID in external system
  externalTimestamp   DateTime?        // When customer consented externally
  evidenceMetadata    String?          // JSON metadata
  actorId             String?          // User ID if staff action, or null if customer
  occurredAt          DateTime         @default(now())
  createdAt           DateTime         @default(now())

  consent             CustomerSmsConsent?   @relation(fields: [consentId], references: [id], onDelete: Cascade)
  disclosureTemplate  SmsDisclosureTemplate? @relation(fields: [disclosureTemplateId], references: [id])

  @@index([businessId, contact, createdAt])
  @@index([consentId])
}

enum ConsentEventType {
  GRANTED
  REVOKED
  REGRANTED
  IMPORTED
  MIGRATED_LEGACY
}

// ── Cryptographic Customer Consent Invitations ──────────────────
model CustomerSmsConsentInvitation {
  id                  String                @id @default(cuid())
  businessId          String
  contact             String                // Normalized E.164
  recipientName       String?
  tokenHash           String                @unique // SHA-256 of raw 32-byte token
  disclosureVersion   String                @default("v1")
  disclosureTemplateId String?
  status              ConsentInviteStatus   @default(PENDING)
  expiresAt           DateTime
  consumedAt          DateTime?
  createdAt           DateTime              @default(now())

  disclosureTemplate  SmsDisclosureTemplate? @relation(fields: [disclosureTemplateId], references: [id])

  @@index([businessId, contact])
  @@index([tokenHash])
}

enum ConsentInviteStatus {
  PENDING
  CONSUMED
  EXPIRED
  REVOKED
}
```

## 3. Customer Consent Journey & Token Architecture

### 3.1 Flow
```
Business Dashboard (Campaign Builder / Review Us Page / API)
        │
        ▼
POST /api/sms/consent/invite
  - Normalizes recipient phone to E.164
  - Generates 32-byte secure random token
  - Stores SHA-256 hash in CustomerSmsConsentInvitation with 7-day TTL
  - Returns invitation URL: /consent/[rawToken]
        │
        ▼
Customer receives & opens /consent/[rawToken]
  - Server hashes rawToken and looks up CustomerSmsConsentInvitation
  - Validates: token exists, status == PENDING, expiresAt > now(), not consumed
  - Resolves Business.name, normalized contact, active SmsDisclosureTemplate (v1)
  - Renders customer consent page:
      * Business name & branding
      * Masked recipient contact (+1 (415) •••-2001)
      * Server-rendered verbatim disclosure text (CTIA compliant: message/data rates, frequency, STOP, HELP)
      * Unchecked checkbox: "I agree to receive text messages from [Business]..."
      * Submit button (disabled until checkbox checked)
        │
        ▼
Customer checks affirmative checkbox & clicks "Grant Consent"
        │
        ▼
POST /api/sms/consent/grant
  - Payload: { token: rawToken, confirmed: true }
  - Server verifies token validity again atomically
  - Server derives businessId, contact, disclosureVersion, verbatim text server-side
  - Marks invitation as CONSUMED (consumedAt = now())
  - Appends GRANTED/REGRANTED event to CustomerSmsConsentEvent with IP, userAgent, timestamp
  - Upserts CustomerSmsConsent record with status: ACTIVE
  - Writes audit log: sms.consent.granted (masked phone)
  - Displays customer confirmation: "Consent Confirmed. Thank you!"
```

## 4. API Redesign & Separation of Concerns

1. **`POST /api/sms/consent/invite`** (Authenticated Business/Org Member)
   - Inputs: `{ businessId: string, contact: string, recipientName?: string }`
   - Generates secure invitation token, stores hash, returns `{ success: true, inviteUrl, expiresAt }`.
   - Audit: `sms.consent.invitation_created`.

2. **`GET /api/sms/consent/public/[token]`** (Public Customer Endpoint)
   - Validates token hash, status, expiration.
   - Returns public sanitized payload: `{ valid: true, businessName: string, maskedContact: string, disclosureText: string, disclosureVersion: string }`.
   - Never exposes business secrets, raw database IDs, or other recipient data.

3. **`POST /api/sms/consent/grant`** (Public Customer Endpoint)
   - Inputs: `{ token: string, confirmed: boolean }`.
   - Derives all legal metadata server-side.
   - Enforces affirmative action (`confirmed === true`).
   - Appends immutable event, updates active state, consumes token atomically.

4. **`GET /api/sms/consent?businessId=...&contact=...`** (Authenticated Business Status)
   - Returns: `{ eligible: boolean, status: string, consentType?: string, consentSource?: string, consentedAt?: string, disclosureVersion?: string }`.
   - Masks sensitive evidence (IP/userAgent/token) from standard status checks.

5. **`POST /api/sms/consent/import`** (Authenticated Business / API Provenance Import)
   - Inputs: `{ businessId: string, items: Array<{ contact: string, externalSystem: string, externalRecordId?: string, originalTimestamp: string, originalDisclosureText: string, evidenceDescription: string }> }`.
   - Requires rigorous provenance. If provenance is complete and meets standard, records `VERIFIED_API_IMPORT`. If incomplete, marks as `UNVERIFIED_LEGACY` (ineligible for SMS).

6. **`POST /api/sms/consent/revoke`** (Authenticated Business or Opt-Out Trigger)
   - Inputs: `{ businessId: string, contact: string, reason?: string }`.
   - Appends `REVOKED` event to `CustomerSmsConsentEvent`.
   - Updates `CustomerSmsConsent.status = REVOKED`.

## 5. UI Updates: Campaign Builder & Review Us Page

### 5.1 Campaign Builder
- **Remove** the checkbox that previously called `recordConsent()`.
- **Add** live consent eligibility check for all SMS recipients.
- Display status badges for each recipient:
  - ✅ **Verified Consent** (Eligible)
  - ⚠️ **Consent Required** (Action: "Copy Consent Link" / "Send Consent Request")
  - 🚫 **Opted Out** (Blocked)
- If dispatching with unconsented SMS recipients, the UI alerts the user that unconsented recipients will be skipped or blocked by the server-side gate.

### 5.2 Review Us Page
- **Remove** the checkbox that previously called `recordConsent()`.
- Check recipient eligibility before send.
- Provide clear workflow for creating customer consent requests.

## 6. Migration Strategy for Existing SMS-002 Data

1. **Assessment**:
   - Existing `CustomerSmsConsent` rows in development or staging may have been generated by the employee checkbox.
2. **Strategy**:
   - Classify existing records where `consentSource` was `MANUAL_ENTRY`, `CHECKOUT_FORM`, or `WEBSITE_FORM` created prior to SMS-002.1 as `UNVERIFIED_LEGACY` unless backed by a cryptographically verified token or signed customer event.
   - Insert corresponding historical `MIGRATED_LEGACY` event in `CustomerSmsConsentEvent`.
   - `hasValidConsent()` will require `status === 'ACTIVE'` AND `consentSource in [CUSTOMER_WEB_FORM, VERIFIED_API_IMPORT, IN_PERSON_KIOSK]` and `consentType === EXPRESS_WRITTEN`. `UNVERIFIED_LEGACY` records will fail closed (`CONSENT_REQUIRED`).

## 7. Verification Plan & Test Suite (CONSENT-201 to CONSENT-235)

### 7.1 Test Matrix in `scripts/test-sms.ts`
- **CONSENT-201**: Customer consent invitation can be created.
- **CONSENT-202**: Consent token is cryptographically unpredictable (256-bit entropy).
- **CONSENT-203**: Expired consent token is rejected.
- **CONSENT-204**: Consumed/replayed token is rejected.
- **CONSENT-205**: Token cannot authorize another business (cross-tenant attack blocked).
- **CONSENT-206**: Token cannot authorize another phone number (contact substitution blocked).
- **CONSENT-207**: Customer consent checkbox is unchecked by default in UI.
- **CONSENT-208**: Customer cannot submit consent without affirmative action (`confirmed: true`).
- **CONSENT-209**: Server determines disclosure text & version; client cannot override.
- **CONSENT-210**: Client cannot inject arbitrary disclosure text.
- **CONSENT-211**: Exact verbatim disclosure text is persisted in event.
- **CONSENT-212**: Disclosure version is persisted in event.
- **CONSENT-213**: Server timestamp is persisted in event.
- **CONSENT-214**: IP address and user-agent captured where available.
- **CONSENT-215**: Consent event ledger is strictly immutable (historical events never modified).
- **CONSENT-216**: Revocation appends historical `REVOKED` event without deleting grant evidence.
- **CONSENT-217**: Re-consent creates a new `REGRANTED` event instead of overwriting history.
- **CONSENT-218**: Previous disclosure remains preserved after re-consent.
- **CONSENT-219**: Business checkbox cannot manufacture customer consent.
- **CONSENT-220**: Campaign endpoint dispatches via `SmsService.sendSms()` and cannot bypass consent.
- **CONSENT-221**: Review Us endpoint dispatches via `SmsService.sendSms()` and cannot bypass consent.
- **CONSENT-222**: Missing consent returns `CONSENT_REQUIRED`.
- **CONSENT-223**: Revoked consent returns `CONSENT_REQUIRED`.
- **CONSENT-224**: OptOut overrides active consent (`RECIPIENT_OPTED_OUT`).
- **CONSENT-225**: START keyword removes opt-out but does NOT manufacture consent.
- **CONSENT-226**: API import without sufficient provenance does not authorize SMS (`UNVERIFIED_LEGACY`).
- **CONSENT-227**: API import with valid structured evidence is classified as `VERIFIED_API_IMPORT`.
- **CONSENT-228**: `MANUAL_ENTRY` cannot create unsupported `EXPRESS_WRITTEN` consent.
- **CONSENT-229**: Legacy business-asserted consent does not automatically authorize SMS.
- **CONSENT-230**: No Telnyx request occurs when consent is missing.
- **CONSENT-231**: No Twilio request occurs when consent is missing.
- **CONSENT-232**: Cross-tenant consent cannot authorize another business.
- **CONSENT-233**: No raw consent token is written to audit logs.
- **CONSENT-234**: No full phone number is written to audit metadata (all masked).
- **CONSENT-235**: Consent status API does not expose sensitive evidence fields to unauthorized users.
