## 2. Telnyx Production Architecture

ReviewReply utilizes a strict orchestrator-adapter architecture with fail-closed security gates:

```
Route Handler (/api/campaigns/create, /api/review-us-page/send)
       ↓
  SmsService (Central Orchestrator)
  ├── 1. Feature Flag / Kill Switch (`FEATURE_SMS_ENABLED === 'true'`)
  ├── 2. Phone Validation & Normalization (Strict E.164 via libphonenumber-js)
  ├── 3. Opt-Out Enforcement (Global `OptOut` table lookup)
  ├── 4. Business & Tenant Verification (DB Lookup + Ownership Assertion)
  ├── 5. Daily Quota Enforcement (UTC Day Window: 100 Trial / 500 Standard)
  ├── 6. Recipient Cooldown Enforcement (14-day window / business / E.164 number)
  ├── 7. Active Provider Resolution (`SMS_PROVIDER` defaults to Telnyx)
  ├── 8. Provider Dispatch (`TelnyxAdapter.send()`)
  ├── 9. Real Provider Message ID Storage (`SmsDeliveryEvent`)
  └── 10. Audit Logging (PII-masked destination number)
       ↓
  Telnyx REST API v2 (`https://api.telnyx.com/v2/messages`)
```

## 3. Provider Selection Behavior

1. **Unset `SMS_PROVIDER`**: Defaults to `TelnyxAdapter`.
2. **Explicit `SMS_PROVIDER=telnyx`**: Selects `TelnyxAdapter`.
3. **Explicit `SMS_PROVIDER=twilio`**: Selects `TwilioAdapter` (only if explicitly configured).
4. **Unknown `SMS_PROVIDER` value**: Defaults safely to `TelnyxAdapter`.
5. **No Silent Fallback**: If a Telnyx API request fails or times out, the message fails closed. `SmsService` **never** automatically delegates or falls back to Twilio upon Telnyx failure (`TELNYX-PROD-035` regression proven).
6. **Isolated Sender Resolution**: Sender number resolution strictly references `TELNYX_FROM_PHONE_NUMBER` for Telnyx sends, preventing accidental cross-provider credential leakage.

## 4. Telnyx Sending Path Hardening

Audit of [telnyx.ts](file:///c:/WEB%20APP/REVIEW%20REPLY/src/lib/sms/telnyx.ts) and [service.ts](file:///c:/WEB%20APP/REVIEW%20REPLY/src/lib/sms/service.ts):

- **Authentication**: Uses `Authorization: Bearer ${process.env.TELNYX_API_KEY}` over HTTPS (`https://api.telnyx.com/v2/messages`).
- **Sender Verification**: Requires either `TELNYX_FROM_PHONE_NUMBER` (E.164) or `TELNYX_MESSAGING_PROFILE_ID`. Missing sender credentials return `CONFIG_MISSING` fail-closed.
- **Destination Validation**: Destination phone numbers must validate against Google's `libphonenumber-js` and format to strict E.164. Non-compliant numbers are rejected with `INVALID_DESTINATION`.
- **Identity Integrity**: Successful Telnyx responses store `data.id` as `providerMessageId`. On rejection or network failure, `providerMessageId` remains `NULL`. Synthetic IDs (`local_*`, `cuid()`, timestamps) are strictly forbidden in production.

## 5. Webhook Cryptographic Security (Ed25519)

Audit of [route.ts](file:///c:/WEB%20APP/REVIEW%20REPLY/src/app/api/webhooks/sms/telnyx/route.ts) and [telnyx.ts](file:///c:/WEB%20APP/REVIEW%20REPLY/src/lib/sms/telnyx.ts):

- **Required Headers**: `telnyx-signature-ed25519` (64-byte Ed25519 signature) and `telnyx-timestamp` (Unix epoch seconds).
- **Public Key**: Decodes raw 32-byte Base64 Ed25519 key from `TELNYX_PUBLIC_KEY` and constructs standard SPKI DER buffer (`302a300506032b6570032100` prefix).
- **Signed Payload**: Evaluates exact signature against `${timestamp}.${rawBody}` using Node.js `crypto.verify(null, signedPayload, publicKey, sigBytes)`.
- **Raw Body Integrity**: Reads `request.text()` before any JSON parsing to guarantee cryptographic byte fidelity.
- **Fail-Closed Matrix**: Missing headers, missing public key, invalid signature, tampered body, malformed key, or malformed signature all immediately terminate with `HTTP 403 Forbidden`.

## 6. Replay Protection Window

- **Threshold**: 300 seconds (`SMS_LIMITS.WEBHOOK_REPLAY_WINDOW_SEC = 300`).
- **Validation**:
  ```typescript
  const eventTime = parseInt(timestamp, 10)
  const currentTime = Math.floor(Date.now() / 1000)
  if (isNaN(eventTime) || Math.abs(currentTime - eventTime) > 300) {
    return false
  }
  ```
- Any webhook event timestamped older than 5 minutes or in the future beyond 5 minutes is rejected with `HTTP 403`.

## 7. Atomic Idempotency & Database Integrity

Idempotency is enforced by the database layer rather than race-prone `findUnique` checks:

```
Incoming Webhook Request
         ↓
  db.smsWebhookEvent.create({
    data: { provider, eventId: event.eventId, ... }
  })
         ↓
  ┌──────────────────────────────┬──────────────────────────────┐
  │         First Delivery       │     Concurrent Duplicate     │
  ├──────────────────────────────┼──────────────────────────────┤
  │ Success (Insert committed)   │ Prisma P2002 Unique Collision│
  │ Proceed to business mutation │ Return HTTP 200 (Idempotent) │
  │                              │ Zero duplicate side effects  │
  └──────────────────────────────┴──────────────────────────────┘
```

- **Genuine Database Errors**: Non-P2002 database exceptions return `HTTP 500` to trigger provider delivery retry rather than falsely reporting success.

## 8. Tenant Isolation Contract

Webhook payloads are treated as untrusted external inputs:

1. **No Payload Trust**: Webhook payloads are never allowed to dictate `businessId`, `orgId`, or `tenantId`.
2. **Strict Inversion of Ownership**: Ownership is resolved strictly backwards from the database:
   $$\text{providerMessageId} \xrightarrow{\text{findUnique}} \text{SmsDeliveryEvent} \xrightarrow{} \text{businessId} \xrightarrow{} \text{Business} \xrightarrow{} \text{Organization}$$
3. **Unknown Message ID Handling**: Webhook delivery receipts for unknown `providerMessageId` values are safely acknowledged and ignored without creating orphaned records or mutating tenant state.

## 9. Delivery State Machine & Monotonic Transitions

Delivery state transitions adhere strictly to monotonic forward progression:

```
QUEUED (0) → SENDING (1) → SENT (2) → DELIVERED (3) → FAILED (4) / UNDELIVERED (5)
```

| Current Status | New Webhook Status | Action | Rationale |
|---|---|---|---|
| `SENT` | `DELIVERED` | Allowed (Update DB) | Standard forward delivery receipt |
| `SENT` | `FAILED` | Allowed (Update DB) | Carrier dispatch failure |
| `DELIVERED` | `SENT` | **Rejected (Ignored)** | Prevents delayed out-of-order webhook regression |
| `DELIVERED` | `DELIVERED` | Idempotent (No-op) | Duplicate webhook acknowledgement |
| `DELIVERED` | `FAILED` | Allowed (Update DB) | Downstream carrier retroactive correction |

## 10. Quota, Cooldown, and Abuse Controls

1. **Daily Tenant Sending Quota**:
   - **Trial / FREE**: 100 SMS / day / business.
   - **Standard / PRO**: 500 SMS / day / business.
   - **Abuse Prevention**: Counts **all** dispatch attempts (including `FAILED`) to prevent infinite failure loops.
   - **Reset**: UTC Midnight (`00:00:00Z`).
2. **Recipient Cooldown**:
   - 14 days between review requests per business per normalized E.164 phone number.
   - Cross-business sends to the same recipient are permitted (strictly business-scoped).
3. **Campaign Batch Limit**:
   - Hard cap of 250 recipients per single campaign batch, enforced at both API route handlers and validation schemas.
4. **Global Kill Switch**:
   - `FEATURE_SMS_ENABLED === 'true'` required. When unset or `false`, returns `FEATURE_DISABLED` immediately with zero network requests.

## 11. Inbound Keyword Handling (STOP, START, HELP)

| Inbound Keyword | Normalized Action | Database Impact |
|---|---|---|
| `STOP`, `UNSUBSCRIBE`, `CANCEL`, `QUIT`, `END` | Opt-Out | Upserts contact into `OptOut` table; logs `sms.opt_out` audit event. |
| `START`, `YES`, `UNSTOP` | Opt-In | Deletes contact from `OptOut` table; logs `sms.opt_in` audit event. |
| `HELP` | Info Request | Non-mutating; logs `sms.help_requested` audit event. |

All inbound phone numbers are normalized to E.164 before querying or persisting opt-out status.
