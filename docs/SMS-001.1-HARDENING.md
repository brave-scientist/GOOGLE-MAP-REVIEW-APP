# SMS-001.1 — Telnyx Production Hardening Documentation

## 1. Architecture

ReviewReply SMS is built on a **provider-abstracted architecture**:

```
Route Handler (campaigns/create, review-us-page/send)
        ↓
   SmsService (orchestrator)
   ├── Kill-switch check (FEATURE_SMS_ENABLED)
   ├── E.164 normalization (libphonenumber-js)
   ├── Opt-out enforcement (OptOut table)
   ├── Business/tenant verification
   ├── Daily quota enforcement (UTC day window)
   ├── Recipient cooldown (14 days/business/number)
   ├── Provider dispatch
   └── Delivery event recording
        ↓
   ISmsProvider interface
   ├── TelnyxAdapter (primary)
   └── TwilioAdapter (fallback)
```

## 2. Provider Abstraction

Both adapters implement `ISmsProvider`:

```typescript
interface ISmsProvider {
  readonly name: 'telnyx' | 'twilio'
  send(options: SmsSendOptions): Promise<SmsSendResult>
  verifyWebhook(rawBody: string, headers: Headers): boolean
  parseWebhook(rawBody: string): ParsedSmsWebhookEvent | null
}
```

**Provider selection**: Controlled by `SMS_PROVIDER` env var. Defaults to `telnyx`.

## 3. Telnyx Configuration

### Required Environment Variables

| Variable | Purpose | Required |
|---|---|---|
| `FEATURE_SMS_ENABLED` | Global kill switch. Must be `"true"` to send. | Yes |
| `TELNYX_API_KEY` | Telnyx v2 API Bearer token | Yes (for sending) |
| `TELNYX_FROM_PHONE_NUMBER` | Verified sender number (E.164) | Yes (or messaging profile) |
| `TELNYX_MESSAGING_PROFILE_ID` | Telnyx messaging profile ID | Optional (alternative to from number) |
| `TELNYX_PUBLIC_KEY` | Ed25519 public key for webhook verification (base64) | Yes (for webhooks) |

### Sender Precedence

1. `options.from` (per-send override) — highest
2. `TELNYX_FROM_PHONE_NUMBER` env var
3. `TELNYX_MESSAGING_PROFILE_ID` env var
4. **If none configured → fail-closed** (`CONFIG_MISSING`)

No fake phone numbers. No silent fallbacks.

## 4. Webhook Security

### Ed25519 Signature Verification

- Header: `telnyx-signature-ed25519` (base64-encoded 64-byte signature)
- Header: `telnyx-timestamp` (Unix epoch seconds)
- Signed payload: `{timestamp}.{rawBody}`
- Public key: `TELNYX_PUBLIC_KEY` (base64-encoded 32-byte raw Ed25519 public key)

### Security Controls

| Control | Implementation |
|---|---|
| Invalid signature | HTTP 403 |
| Missing signature | HTTP 403 |
| Missing timestamp | HTTP 403 |
| Missing public key | HTTP 403 (fail-closed) |
| Timestamp > 300s old | HTTP 403 (replay protection) |
| Malformed timestamp | HTTP 403 |
| Malformed JSON | HTTP 400 |
| Unknown event type | `parseWebhook()` returns null → HTTP 400 |
| Missing event ID | `parseWebhook()` returns null → HTTP 400 |

## 5. Atomic Idempotency

### Problem (Pre-Hardening)

```
findUnique(eventId) → not found
                    ← concurrent request also gets "not found"
create(eventId) → success
                ← concurrent create(eventId) → also success (DUPLICATE!)
```

### Solution (Post-Hardening)

```
create(eventId) → success OR P2002 unique constraint error
                ← P2002 → return 200 "already processed" (atomic)
```

The `SmsWebhookEvent.eventId` `@unique` constraint is the authoritative idempotency gate. Two concurrent requests with the same eventId result in exactly one successful insert; the second gets `P2002` and returns HTTP 200 without any mutation.

**Genuine database errors** (connection failure, etc.) are distinguished from duplicates and return HTTP 500.

## 6. Delivery Status Model

### Status Values

| Status | Ordinal | Meaning |
|---|---|---|
| `QUEUED` | 0 | Message accepted, waiting for dispatch |
| `SENDING` | 1 | Dispatch in progress |
| `SENT` | 2 | Provider accepted the message |
| `DELIVERED` | 3 | Carrier confirmed delivery |
| `FAILED` | 4 | Provider/carrier rejected the message |
| `UNDELIVERED` | 5 | Carrier could not deliver |

### Monotonic Transition Rules

- Status can only move **forward** (higher ordinal) or remain the same (idempotent).
- `DELIVERED → SENT` is **rejected** (prevents delayed webhook regression).
- `DELIVERED → FAILED` is **allowed** (provider can correct initial delivery confirmation).
- A duplicate `DELIVERED` event is silently accepted (idempotent).
- Unknown `providerMessageId` events do not create arbitrary state.

## 7. Tenant Isolation

Webhook payloads are **untrusted**. The system never reads tenant/business/org identifiers from webhook data.

Tenant resolution:
```
providerMessageId (from webhook)
    ↓ findUnique
SmsDeliveryEvent
    ↓ relation
businessId → Business → organizationId
```

If `providerMessageId` doesn't match any `SmsDeliveryEvent`, the webhook is silently ignored — no arbitrary records are created or mutated.

## 8. Quota Policy

### Daily Limits

| Plan | Daily Limit | Enforcement |
|---|---|---|
| FREE / unset | 100 SMS/day/business | `sentTodayCount >= 100 → reject` |
| STANDARD+ | 500 SMS/day/business | `sentTodayCount >= 500 → reject` |

### What Counts

**All dispatch attempts count**, including FAILED ones. This prevents abuse loops where an attacker circumvents limits by causing intentional failures.

### Campaign Batch Limit

Maximum 250 recipients per campaign batch. Enforced server-side in both campaign create and review-us-page send routes.

### Day Boundary

Quota resets at **UTC midnight** (`setUTCHours(0,0,0,0)`).

## 9. Cooldown Policy

**Rule**: 1 SMS review request per recipient per business every 14 days.

**Scope**: `businessId + E.164 normalized recipient number`

- Same business + same number within 14 days → **reject** (`RECIPIENT_COOLDOWN_ACTIVE`)
- Same business + same number after 14 days → **allow**
- Same number + different business → **allow** (cooldown is business-scoped)
- Different formatting of same number → **same E.164** (e.g., `(415) 555-2671` = `415-555-2671` = `+14155552671`)
- Failed/non-dispatched attempts: Only `SENT`, `DELIVERED`, and `QUEUED` statuses trigger cooldown

## 10. STOP / START / HELP Behavior

### Keywords

| Keyword | Action |
|---|---|
| STOP, CANCEL, QUIT, UNSUBSCRIBE, END | Opt-out (suppress future SMS) |
| START, YES, UNSTOP | Remove opt-out |
| HELP | Log only (no opt-in/opt-out mutation) |

### Normalization

- Case-insensitive: `stop` = `STOP` = `Stop`
- Whitespace-trimmed: `" STOP "` → `STOP`
- Inbound phone numbers normalized to E.164 before opt-out storage
- Duplicate STOP is idempotent (upsert)

## 11. Consent vs Opt-Out Distinction

### Current State

| Capability | Status |
|---|---|
| **Opt-Out tracking** | ✅ Implemented (`OptOut` model) |
| **Positive consent evidence** | ❌ Not yet implemented |

### What Opt-Out Answers

> "Has this contact opted out of receiving SMS?"

### What Consent Answers (NOT YET IMPLEMENTED)

> "Was this contact authorized to receive SMS? When? Where? Under what disclosure?"

### Compliance Gap

For full TCPA/CASL compliance, ReviewReply needs a `CustomerSmsConsent` model with:
- `businessId` — which business obtained consent
- `contact` — E.164 phone number
- `channel` — SMS
- `consentType` — express_written | implied | transactional
- `source` — web_form | in_person | import
- `consentText` — the actual disclosure shown
- `consentedAt` — timestamp
- `revokedAt` — nullable (filled when STOP received)

**This is a remaining commercial-launch prerequisite.**
